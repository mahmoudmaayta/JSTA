7. Complaints about travel offices  
   (شكاوى مكاتب السياحة)

--------------------------------
A. HIGH-LEVEL DESIGN GOAL
--------------------------------

Extend the system so that:

- INTERNAL AUTOMATION:
  JSTA staff can manage, track, and report on:
  membership cards, inspections, oversight, unlicensed offices, staff experience verification, office compliance, and complaints.

- DIGITAL SYSTEM FOR OFFICES:
  Each office, via its portal, can view and (where appropriate) interact with:
  its membership status, inspections history and actions required, staff experience status, compliance status, and complaints related to it.

Keep the UX simple: use tabs, cards, and short labels (Arabic/English).

--------------------------------
B. DATA MODEL & DATABASE CHANGES
--------------------------------

Extend the existing PostgreSQL schema. Add migrations instead of manual SQL.

Design and/or extend the following entities (you can adapt field names to match existing conventions):

1) Membership Cards
   Table: membership_cards
   Fields:
   - id (PK)
   - office_id (FK → offices)
   - membership_number (string)
   - status: ["pending", "active", "suspended", "expired"]
   - issued_at (timestamp)
   - expires_at (timestamp)
   - notes (text, optional)

   Rules:
   - One active membership per office.
   - Historical records are allowed.

2) Inspections (Field Visits)
   Table: inspections
   Fields:
   - id
   - office_id (FK)
   - scheduled_at (timestamp)
   - inspector_name (string)
   - visit_type: ["initial", "routine", "follow_up"]
   - status: ["scheduled", "completed", "cancelled"]
   - findings (text)
   - violations (text or JSON)
   - actions_required (text)
   - created_by_admin_id (FK to admin user, if exists)
   - created_at, updated_at

3) Member Advocacy
   Table: advocacy_cases
   Fields:
   - id
   - office_id
   - title
   - description
   - case_type (string or enum)
   - status: ["open", "in_progress", "resolved", "closed"]
   - opened_at
   - closed_at (nullable)
   - internal_notes (text)

4) Oversight & Unlicensed Offices
   Table: oversight_records
   Fields:
   - id
   - office_id (nullable FK if mapped to a known office)
   - office_name (string)
   - office_type (string)
   - license_status: ["licensed", "unlicensed", "suspended"]
   - source (string: complaint, ministry, inspection, etc.)
   - actions_taken (text)
   - status: ["under_review", "action_required", "resolved"]
   - created_at, updated_at

5) Staff Experience Certification
   Assume we already have a staff/employees table linked to offices.
   Extend with:
   - employment_start_date (date)
   - employment_end_date (date, nullable)
   - role_title (string)
   - experience_verified (boolean, default false)
   - experience_verified_at (timestamp, nullable)
   - verified_by_admin_id (FK, nullable)
   - staff_notes (text, optional)

6) Office Regulation / Compliance
   Extend the offices table with:
   - office_category (string, e.g. "A", "B", "C" or type code)
   - compliance_status: ["compliant", "warning", "non_compliant"]
   - last_compliance_review_at (timestamp)

7) Complaints
   Either extend the existing complaints table or create a dedicated one:
   Table: complaints
   Fields:
   - id
   - office_id (FK)
   - complainant_type: ["office", "customer", "internal"]
   - subject (string)
   - description (text)
   - attachments (JSON or separate table for uploaded files)
   - status: ["submitted", "under_review", "resolved", "closed"]
   - decision (text, nullable)
   - resolution_date (timestamp, nullable)
   - created_at, updated_at

C. BACKEND: API & BUSINESS LOGIC
--------------------------------

1) For each new entity above:
   - Add REST endpoints under a sensible route namespace, e.g.:
     - /api/membership-cards
     - /api/inspections
     - /api/advocacy-cases
     - /api/oversight-records
     - /api/staff-experience
     - /api/complaints
   - Implement:
     - list (with filters)
     - get by id
     - create
     - update
     - (optional) soft delete where appropriate

2) Apply role-based access control (RBAC):
   - Admin:
     - Full CRUD for all entities.
   - Office:
     - Can view its own data (membership, inspections, complaints, staff).
     - Can create advocacy cases and some types of complaints if needed.
     - Cannot edit admin-only fields (decisions, verification flags, etc.).

3) Connect workflows:
   - On renewal approval:
     - Optionally auto-create or update membership_cards for that office.
   - On completed inspections:
     - Optionally update office.compliance_status based on violations.
   - On complaint resolution:
     - Set status and resolution_date.
   - On staff verification:
     - Set experience_verified and experience_verified_at.

--------------------------------

Add or extend admin views to manage the new modules:

1) Membership Module:

2) Inspections Module:

3) Advocacy Cases:
   - Table view: office, case_type, status.
   - Detail view: description, internal_notes.
   - Ability to update status and notes.

4) Oversight:
   - List of oversight_records.
   - Filter by license_status and status.

5) Staff Experience:

   - Show verification date and notes.

6) Complaints:
   - Table view by status, complainant_type.
   - Detail view with description, attachments, and decision.
   - Ability to update status and record decision.

Use existing UI components, table patterns, and modals. Keep RTL and Arabic labels consistent with the rest of the app.
